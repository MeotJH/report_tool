# 문서 유형별 기능 공백 분석

두 가지 실제 서류를 이 편집기로 만들어 보고 막히는 지점을 기록했다.

- **사례 A — 임금명세서** (급여담당자): 1~5장
- **사례 B — 비밀유지서약서** (인사담당자): 6장

**전제 (사례 A)**: A사 급여담당자가 이 편집기만으로 2026년 8월 임금명세서 양식을 만들어
직원 120명에게 발행해야 한다. 텍스트·상자·선·표로 A4를 그리고, 각 자리에 데이터를
1:1로 붙이는 것이 목표다.

**방법**: 실제 편집기(`npm run dev:designer`)를 띄워 양식을 만들어 보고, 막히는
지점마다 해당 코드를 확인했다. 아래 항목은 전부 코드로 확인한 것이다.

**법적 요건 근거**: 근로기준법 §48②, 시행령 §27의2 — 임금명세서에는 구성항목별
**금액**과 **계산방법**, 공제항목별 **금액과 계산내역**을 반드시 적어야 한다.

## 0. 결론 먼저

| 등급 | 뜻 | 개수 |
|---|---|---|
| **P0** | 이게 없으면 서류를 **만들 수 없다** | 10 |
| **P1** | 만들 수는 있으나 **사고가 나거나** 담당자가 개발자를 불러야 한다 | 13 |
| **P2** | 양식 품질·작업 속도 문제 | 12 |

> P0-7·P0-8은 사례 B(6장), P0-9·P0-10은 사례 C(7장)에서 발견했다.

가장 큰 구멍은 세 가지다.

1. **표가 "고정 라벨 + 변수 금액"을 표현하지 못한다.** 급여명세서 표의 90%가 이 모양인데,
   현재 표는 전부 고정이거나 전부 배열이다. → 사용자가 요청한 *표 고정값 / 표 변수값*의
   조합이 지금 구조로는 불가능하다.
2. **합계를 계산할 수 없다.** 지급액 계·공제액 계·실지급액을 템플릿이 못 만든다.
   수당 하나 추가할 때마다 담당자가 개발자에게 필드 추가를 요청해야 한다 —
   이 제품의 존재 이유가 여기서 깨진다.
3. **포맷을 지정할 UI가 없다.** 도메인·PDF는 통화/날짜/마스킹을 전부 지원하는데
   편집기에 입력칸이 없어서 `4200000`이 그대로 찍힌다.

## 1. P0 — 없으면 만들 수 없다

### P0-1. 표에서 "고정 라벨 + 변수 값"을 못 섞는다

실제 급여명세서 지급 표는 이렇게 생겼다.

| 항목 | 금액 |
|---|---|
| 기본급 (고정 문구) | `{{pay.base}}` (변수) |
| 식대 (고정 문구) | `{{pay.meal}}` (변수) |

`TableSource`는 `StaticTableSource`(모든 셀을 템플릿에 저장) 또는
`BoundTableSource`(모든 행을 배열에서) **둘 중 하나**다
(`packages/core/src/domain/element/TableSource.ts`).

정적 셀에 `{{pay.base}}`를 타이핑해 봤다. **문자 그대로 찍힌다.**
`TableColumn.cellTemplate`이 `{{row.amount}}`이고, `TemplateExpression.render`가
행 객체에서 꺼낸 문자열 `"{{pay.base}}"`를 2차 치환 없이 반환하기 때문이다.
경고도 없다.

**필요한 것**: 셀 단위 바인딩. `TableCellValue`에 `{ kind: "binding", path, formatSpec }`
같은 갈래를 추가하거나, 정적 셀 문자열을 `TemplateExpression`으로 한 번 더 해석한다.

### P0-2. 합계·사칙연산이 없다

`TemplateExpression`은 `{{경로}}` 치환만 한다
(`packages/core/src/domain/element/TemplateExpression.ts`). `sum()`도 `+`도 없다.

- 지급액 계 / 공제액 계 / 실지급액 → 만들 수 없다
- 표 합계 행(footer) → `TableElement`은 header + body만 그린다
- 행 안 계산(`시간 × 단가`) → 안 된다

**필요한 것**: 안전한 식 평가 계층. 최소 `sum(배열.필드)`, `+ - * /`, 괄호.
`TemplateExpression`을 확장하지 말고 별도 `Formula` 값 객체 + Visitor로 분리하는 편이
좋다(치환과 계산은 실패 방식이 다르다).

### P0-3. 계산방법을 적을 수단이 없다

법이 요구하는 `연장근로 12시간 × 15,000원 × 1.5 = 270,000원` 같은 문장을
템플릿이 만들 수 없다. P0-2가 없으면 호스트가 이 문장을 통째로 문자열로 계산해
넘겨야 하고, 그러면 명세서 양식을 바꿀 때마다 서버 코드를 고쳐야 한다.

### P0-4. 필드 표시 형식(포맷)을 지정할 UI가 없다

`Binding.formatSpec`은 도메인에 있고 `BindingResolver`·`PdfElementVisitor`가 전부
적용한다. 그런데 `ElementInspectorVisitor.visitField`에는 "값 없을 때 / 필수 값 / 글자"
세 칸뿐이고 **포맷 입력칸이 없다**
(`packages/designer/src/view/inspector/ElementInspectorVisitor.tsx`).

→ 금액은 `4200000`, 날짜는 `2026-08-25T00:00:00.000Z` 원본이 그대로 나간다.

이전에는 민감 필드에 마스킹을 자동 제안하는 경로가 유일하게 있었는데, 호스트 스키마를
제거하면서 그 출처(`sensitive`)가 사라졌다. 지금은 **어떤 포맷도 UI로 지정할 수 없다.**

### P0-5. 표 열의 포맷이 렌더링에서 무시된다

`TableColumnPlanner`가 currency/number/date 포맷을 열에 저장하는데,
`KonvaElementVisitor.bodyRows`와 `PdfElementVisitor.visitTable` 둘 다
`TemplateExpression.render(column.cellTemplate, { row })`만 부르고 포맷터를 거치지 않는다.
열 포맷을 바꾸는 UI도 없다. (`TASKS.md` T57-U로 이미 등록되어 있음)

### P0-6. 선언한 변수에 미리보기 값을 줄 수 없다

`sampleData`는 호스트가 생성자에 주입한 고정 객체이고 편집기에서 바꿀 수 없다
(`EditorController.getSampleData`). 담당자가 `pay.bonus`를 선언하고 문서에 놓으면
미리보기는 **영원히 빈칸**이다.

사용자가 요구한 "데이터와 텍스트 요소의 1:1 대응"을 눈으로 확인할 방법이 없다는 뜻이다.
**변수 선언 시 예시값을 함께 입력받고 미리보기가 그 값을 쓰게 하는 것이 이 기능의 전제다.**

## 2. P1 — 사고가 나거나 개발자를 불러야 한다

### P1-1. 표 행이 넘치면 조용히 잘린다 (데이터 유실)

`PdfElementVisitor.visitTable`은 `(rowIndex + 1) * rowHeight > frame.height`면
`break`한다. 수당이 6개인 직원의 명세서에서 **마지막 두 줄이 사라진 채 발행된다.**
경고도 로그도 없다.

더 나쁜 것은 **설계 화면에서 이 사고를 볼 수 없다**는 점이다.
`KonvaElementVisitor.sampleRows`는 최대 3행만 그리고, 캔버스는 프레임 밖으로 넘친 행을
클리핑하지 않는다. 담당자는 미리보기에서 멀쩡한 표를 보고 발행 버튼을 누른다.

`TableOverflow`는 `"clip"` 한 가지뿐이라 "행 높이 자동 축소"나 "다음 페이지"라는
대안조차 고를 수 없다.

### P1-2. 민감 필드 마스킹이 없다

주민등록번호를 문서에 놓으면 `9001011234567`이 평문으로 찍힌다.
`MaskFormatter`는 구현되어 있으나 (a) 변수에 민감 표시를 달 수 없고
(b) 포맷을 고를 UI가 없다(P0-4). 개인정보 사고 경로다.

**필요한 것**: `TemplateVariable`에 `sensitive` 추가 → 배치 시 마스킹 기본 제안 부활.

### P1-3. 변수 이름·라벨·타입을 고칠 수 없다

`EditorActions.updateVariable`은 구현되어 있는데 **화면에서 호출하는 곳이 없다.**
지금은 지우고 다시 만드는 수밖에 없고, 그러면 이미 배치한 요소의 바인딩이 미아가 된다
(경고만 뜬다). 게다가 `updateVariable`은 자식 선언 경로만 옮기고 **요소의 바인딩은
따라가지 않는다.**

### P1-4. 선언 `required`가 아무 일도 하지 않는다

`TemplateVariable.required`(선언 단위)와 `Binding.required`(요소 단위)가 따로 논다.
"필수"로 선언해도 그 경로를 문서 어디에도 쓰지 않으면 아무도 알려주지 않는다.
반대로 문서에서 지워도 선언은 필수인 채로 남는다.

### P1-5. 쓰이지 않는 선언을 경고하지 않는다

`TemplateIssueFinder`는 "정의되지 않은 경로를 참조한다"만 잡는다.
반대 방향("선언했는데 문서에 없다")이 없어서, 담당자가 변수를 만들어 놓고
배치를 빠뜨린 것을 발행 전에 알 수 없다.

### P1-6. 로고·직인 이미지를 넣을 수 없다

`ImageElement`는 `assetId` 문자열만 받고, Inspector는 "호스트가 해석할 식별자"를
**손으로 타이핑**하게 한다. 업로드도 미리보기도 없다. 담당자는 회사 직인이 제대로
들어갔는지 발행 전까지 알 수 없다.

### P1-7. 템플릿 저장·열기·이름 변경이 없다

`Template.rename`은 구현되어 있으나 UI에 없다(헤더의 이름은 읽기 전용 pill).
저장은 `onChange`로 JSON을 뱉는 게 전부고, 목록·불러오기 화면이 없다.
담당자는 자기가 만든 양식을 다시 열 수 없다.

### P1-8. PDF 미리보기가 없다

캔버스는 근사치다(`ARCHITECTURE.md` 6.2가 직접 그렇게 적고 있다).
실제 줄바꿈·글자 폭·표 잘림은 PDF에서만 확인된다. (`TASKS.md` T57-V)

### P1-9. 문장 안에 변수를 끼워 넣을 방법이 사실상 없다

`2026년 8월분 급여명세서`, `{{employee.name}} 귀하`처럼 **고정 문구와 변수가 한 줄에
섞이는 자리**가 급여명세서에는 여러 개 있다.

`TextElement.content.kind = "template"`이 이것을 지원하고 `ContentResolver`도 해석하는데,
쓰려면 Inspector에서 종류를 "데이터 문구"로 바꾼 뒤 `{{employee.name}}`을 **경로째로
직접 타이핑**해야 한다. 팔레트에서 문장 안으로 변수를 끌어다 놓는 경로가 없다.

담당자는 `employee.name`이라는 내부 경로를 외우고 있어야 하고, 오타를 내면
`TemplateIssueFinder`가 경고를 주기는 하지만 발행 자리는 빈칸이 된다.

**필요한 것**: 캔버스 텍스트 편집 중 팔레트 항목을 넣으면 커서 위치에 토큰이 삽입되고,
편집기에는 경로가 아니라 표시 이름(칩)으로 보이는 것.

### P1-10. 대응 관계를 한쪽 방향으로만 볼 수 있다

팔레트 행을 누르면 그 경로를 쓰는 요소가 캔버스에서 강조된다(`setHighlightedPath`).
그런데 **반대 방향이 없다** — 캔버스에서 필드를 선택해도 팔레트의 해당 행은 강조되지
않고, Inspector는 경로 문자열만 칩으로 보여 준다.

"이 자리에 무엇이 연결됐는지"와 "이 데이터가 어디에 쓰이는지"는 담당자가 양식을
검수할 때 둘 다 필요하다. 지금은 후자만 된다.

### P1-11. 다중 페이지가 없다

`Template`은 `PageSpec` 하나, 요소에 페이지 인덱스가 없다. 급여명세서 1장은 되지만
근로계약서는 안 된다. 저장 스키마 변경이라 `schemaVersion` 2 + 마이그레이션이 필요하다.
(`TASKS.md` T57-W)

## 4. 권장 착수 순서

각 단계가 끝나면 급여담당자가 실제로 **한 걸음 더 나아갈 수 있는지**로 끊었다.

1. **P0-6 변수 예시값** — 이게 있어야 만든 것을 확인할 수 있다. 다른 모든 검증의 전제.
2. **P0-4 + P0-5 포맷 UI와 열 포맷 적용** — 금액이 금액처럼 보인다. 도메인은 이미 다 있다.
3. **P1-2 민감 표시** — 2번에 얹으면 코드가 거의 안 는다. 개인정보 사고를 먼저 막는다.
4. **P0-1 셀 단위 바인딩** — 급여명세서 표가 비로소 만들어진다. 사용자가 요청한 핵심.
5. **P1-1 표 넘침 처리** — 발행 사고를 막는다. 최소한 설계 화면에서 잘림이 보여야 한다.
6. **P0-2 + P0-3 계산식** — 합계·계산방법. 담당자가 개발자에게서 독립한다.
7. **P1-9 문장 안 변수 삽입 + P1-10 역방향 강조** — 1:1 대응이 양방향으로 확인된다.
8. **P1-3 / P1-4 / P1-5 선언 편집과 검증** — 양식을 유지보수할 수 있게 된다.
9. **P1-7 / P1-8 저장·PDF 미리보기** — 실제 업무 루프가 닫힌다.
10. 나머지 P2.

# 6. 사례 B — 비밀유지서약서 (인사담당자)

**전제**: 인사담당자가 신규 입사자에게 받을 비밀유지서약서 양식을 만든다.
제목·전문·제1~5조·서약 문구·서명란·수신처로 구성된 전형적인 1장짜리 서약서다.

**방법**: 현재 도메인 요소만으로 실제 서약서 템플릿을 구성해 (a) 편집기 캔버스에
띄우고 (b) `PdfDocumentRenderer`로 실제 PDF를 뽑아 둘을 비교했다.

## 6.1 되는 것

급여명세서와 겹치지 않는, 계약서류 쪽에서 **잘 동작한 것**들이다.

| 항목 | 상태 |
|---|---|
| 제목·구분선·조문 제목·본문 문단 배치 | 문제없다 |
| 고정 문구 + 변수 혼합 (`본인 {{employee.name}}(은)는 …`) | **렌더링은 정확하다** (작성 방법은 P1-9) |
| 서명란 상자 + 라벨/값 4쌍 | 정확하다 |
| 서명 요소 (점선 + 안내 문구) | 정확하다 |
| 한글 폰트 임베딩·서브셋 | 정확하다. 글자 깨짐 없음 |
| 변수 선언 (`company.name`, `agreement.durationYears` 등 7개) | 정확하다 |

서약서는 표가 거의 없고 텍스트가 중심이라, **역설적으로 급여명세서보다 잘 나온다.**
P0-1(표 혼합)·P0-2(합계)가 걸리지 않기 때문이다.

## 6.2 P0-7 — 문단 줄바꿈(`\n`)이 PDF에서 깨진다 **[신규·최우선]**

각 호를 줄바꿈으로 나눈 조문을 넣었다.

```
본 서약서에서 "비밀정보"라 함은 … 다음 각 호의 어느 하나에 해당하는 것을 말한다.
1. 제품의 설계도, 소스코드, 알고리즘 등 기술 자료
2. 고객 명단, 거래 조건, 가격 정책 등 영업 자료
3. 인사·급여·재무에 관한 자료
4. 그 밖에 회사가 비밀로 관리하는 일체의 정보
```

**발행된 PDF에서는 이렇게 나온다.**

```
본 서약서에서 "비밀정보"라 함은 … 해당하는 것을
말한다.
인사·급여·재무에 관한 자료          ← 3호가 위로 올라오고
1. 제품의 설계도, 소스코드, 알고리즘 등 기술 자료   ← 줄이 겹친다
4. 그 밖에 회사가 비밀로 관리하는 일체의 정보
2. 고객 명단, 거래 조건, 가격 정책 등 영업 자료
```

**호 번호 순서가 뒤엉키고 줄이 서로 겹쳐 판독이 불가능하다.**

### 원인

`PdfTextLayout`은 `\n`을 줄 구분자로 취급하지 않는다.
`WrapTextStrategy.layout`이 `text.split(" ")` — **공백으로만** 쪼갠다.
실제로 측정해 보면 이렇다.

```
우리가 계산한 줄 수: 3
  [0] \n포함=false :: "본 서약서에서 "비밀정보"라 함은 … 해당하는 것을"
  [1] \n포함=true  :: "말한다.\n1. 제품의 설계도 … 영업 자료\n3."
  [2] \n포함=true  :: "인사·급여·재무에 관한 자료\n4. 그 밖에 …"

실제로 종이에 찍히는 줄 수: 7
```

우리 코드는 **3줄**이라 믿고 `firstBaseline - index × fontSize × lineHeight`로 3칸만
띄운다. 그런데 pdf-lib의 `drawText`는 그 안의 `\n`을 **자기 기본 줄높이로 또** 쪼개서
총 7줄을 그린다. 두 줄바꿈 체계가 충돌해 겹친다.
`"3."`이 [1]의 끝, `"인사·급여·재무에 관한 자료"`가 [2]의 시작으로 **찢어진 것**도
공백 단위로만 자르기 때문이다.

### 필요한 것

`PdfTextLayout.layout`이 가장 먼저 `text.split("\n")`으로 문단을 나누고, 문단마다
줄바꿈 전략을 적용한 뒤 결과를 이어 붙여야 한다. 지금은 문단 개념 자체가 없다.

## 6.3 P0-8 — 넘치는 텍스트를 캔버스는 자르고 PDF는 삐져나간다 **[신규]**

같은 조문에서 **캔버스와 PDF가 서로 다르게 틀린다.**

| | 4호 "그 밖에 회사가 비밀로 관리하는 일체의 정보" |
|---|---|
| 편집기 캔버스 | **조용히 사라진다.** `Konva.Text`에 `height`를 주면 안 들어가는 줄을 렌더하지 않는다 |
| 발행 PDF | **그려진다.** `drawTextBox`는 `frame.height`를 아예 보지 않고 계산된 줄을 전부 그린다 |

즉 담당자는 편집기에서 **4호가 없는** 서약서를 보며 "3호까지구나" 하고 확정하고,
직원은 **4호가 있는(그러나 겹쳐서 읽을 수 없는)** 서약서에 서명한다.
계약서류에서 이건 단순 레이아웃 결함이 아니라 **무엇에 서명했는지가 달라지는 문제**다.

`ARCHITECTURE.md` 6.2가 "미리보기와 발행본이 다른 코드로 그려지면 반드시 어긋난다"고
적어 둔 바로 그 사고가 실제로 나 있다.

### 필요한 것

- 두 렌더러가 **같은 줄바꿈 계산**을 공유해야 한다 (`PdfTextLayout`을 core로 올리고
  Konva는 계산된 줄만 그리게 한다)
- 넘칠 때 자르든 늘리든, **조용히 하지 말고 편집기에 경고를 띄운다**
  (`TemplateIssueFinder`에 "요소 영역보다 문구가 길다" 추가)

## 6.4 P1-12 — 조문을 넣거나 지우면 아래를 전부 손으로 옮겨야 한다 **[신규]**

모든 요소가 절대 mm 좌표다. 제2조에 항을 하나 더하면 제3~5조·서약 문구·서명란·수신처를
**전부 끌어내려야 한다.** 서약서는 조문 추가·삭제가 잦은 문서라 이게 실질적으로
가장 큰 작업 부담이다. 급여명세서는 격자가 고정이라 이 문제가 안 보였다.

**필요한 것**: 세로로 흐르는 문단 블록(순서대로 쌓이고 앞이 길어지면 뒤가 밀리는 컨테이너).
지금 구조에는 이 개념이 없다.

## 6.5 서약서에서 특히 아픈 기존 항목

| 항목 | 서약서에서의 의미 |
|---|---|
| **P1-11 다중 페이지** | 조항이 조금만 늘어도 A4 한 장을 넘는다. 실무 서약서·근로계약서는 2~3장이 기본이라 **사실상 차단** |
| **P1-9 문장 안 변수 삽입** | 서약서는 본문 자체가 혼합 문구다. `{{employee.name}}`을 경로째 타이핑해야 하는 게 급여명세서보다 훨씬 자주 발생 |
| **P2-8 한국식 날짜** | `2026-08-23`으로 찍힌다. 서약서 날짜는 `2026년 8월 23일`이어야 한다. 실제 렌더 결과에서 확인됨 |
| **P1-6 직인 이미지** | 회사 직인·간인이 없으면 서약서 효력 다툼의 소지가 된다 |
| **P2-12 그룹화** | 조문 제목+본문이 늘 한 쌍인데 묶을 수 없어 항상 두 번 선택해야 한다 |

## 6.6 서약서 전용으로 새로 필요한 것 (P2)

- **문단 들여쓰기 / 문단 간격 / 첫 줄 들여쓰기** — `TextStyle`에 없다
- **자동 조문 번호** (`제N조`, `①②③`) — 손으로 타이핑하면 조문을 끼울 때 전부 다시 쓴다
- **부분 서식** (한 문단 안에서 특정 어구만 굵게/밑줄) — `TextElement`은 문단 전체에 스타일 하나
- **간인·정정인 자리**, **연명 서명**(회사 대표 + 본인) — `SignatureElement`은 서명자 1명 기준

## 6.7 결론

> **비밀유지서약서는 "만들 수는 있으나 지금 발행하면 안 되는" 상태다.**

- 표 중심 기능(P0-1, P0-2)에 걸리지 않아 **급여명세서보다 진입이 쉽다**
- 그러나 텍스트 중심이라 **P0-7(줄바꿈 깨짐)과 P0-8(캔버스≠PDF)에 정면으로 부딪힌다**
- 그리고 **P1-11(다중 페이지)** 때문에 실무용 2~3장짜리 계약서는 아직 불가능하다

착수 순서에 **P0-7과 P0-8을 1순위로 올려야 한다.** 둘 다 계약서류만의 문제가 아니라
급여명세서의 긴 비고란·계산방법 문구에서도 똑같이 터지고, 무엇보다
**"미리보기와 발행본이 같다"는 제품의 근본 약속이 지금 지켜지지 않고 있다.**

# 7. 사례 C — 표 열을 직접 만들고 데이터에 붙여 보기

사용자가 실제로 부딪힌 경로를 그대로 재현했다. 전부 브라우저에서 눌러 확인한 결과다.

## 7.1 P0-9 — 새로 추가한 열은 데이터에 연결할 방법이 없다 **[신규·최우선]**

`속성 → 열 → ＋ 열 추가`를 누르면 이런 열이 생긴다.

```json
{ "key": "column3", "header": "열 3", "cellTemplate": "{{row.column3}}" }
```

`column3`은 어느 데이터에도 없는 이름이다. 그런데 이걸 바꿀 방법이 **세 겹으로 막혀 있다.**

1. **Inspector에서 못 고친다.** 열 카드에 `{{row.column3}}`이 보이긴 하는데
   `<span class="rt-token-chip--muted">` — **읽기 전용 표시**다. 입력칸도 선택 목록도 없다.
   고칠 수 있는 건 헤더·너비·정렬 세 가지뿐이다.
2. **유일한 연결 수단이 드래그뿐이다.** 팔레트의 배열 자식(`payItems.test`)을 캔버스의
   그 열 위로 끌어다 놓아야 `BindTableColumnCommand`가 돈다. 화면 어디에도 이 사실을
   알려주는 안내가 없다.
3. **그런데 그 드래그가 물리적으로 불가능하다.** → P0-10 참조.

## 7.2 P0-10 — 열을 추가하면 표 프레임 밖으로 삐져나간다 **[신규]**

`＋ 열 추가`는 열을 20mm 폭으로 붙이기만 하고 **표 프레임 너비를 늘리지 않는다.**

```
표 프레임 : x=20,  width=170   → 20mm ~ 190mm
열 너비 합 : 110 + 60 + 20 = 190 → 20mm ~ 210mm   (20mm 초과)
```

새 `column3`이 차지하는 구간은 **190mm ~ 210mm**, 즉 표 프레임(~190mm) **바깥**이자
A4 오른쪽 끝이다. 결과는 이렇다.

- **드롭이 안 된다.** `findElementAt`은 `frame.contains()`로 판정하므로 190mm를 넘는
  지점에서는 표를 찾지 못한다. 그 열 위에 데이터를 놓을 수가 없다 → P0-9가 완결된다.
- **경고도 없다.** `TemplateIssueFinder.isOutsidePage`는 **프레임**만 본다
  (`190 ≤ 210`이라 통과). 열이 종이 밖으로 나가도 아무 말이 없다.
- **캔버스도 PDF도 프레임 밖에 그대로 그린다.** 표에 클리핑이 없다.

### 덤으로 발견한 것: 도달 가능한 열에 놓으면 기존 열을 말없이 덮어쓴다

프레임 안쪽(x=185mm)에 `payItems.test`를 떨어뜨려 봤다. 그 지점은
`columnIndexAtOffset` 기준 **2번째 열(금액)** 이다.

```
변경 전 : item / 항목 · amount / 금액 · column3 / 열 3
변경 후 : item / 항목 · test / 테스트 · column3 / 열 3     ← 금액 열이 사라짐
```

**금액 열이 확인 없이 교체됐다.** Undo는 되지만 알림조차 없다.
표 전환(`convertTable`)은 사라지는 행 수를 알려 주는데, 열 재연결은 알려 주지 않는다.

### 필요한 것

- `＋ 열 추가`가 프레임 너비를 함께 늘리거나, 기존 열에서 폭을 나눠 갖는다
- 열 카드에 **데이터 선택 드롭다운**을 둔다 (드래그는 보조 수단이어야 한다)
- 열 너비 합이 프레임을 넘으면 `TemplateIssueFinder`가 경고한다
- 이미 연결된 열을 덮어쓸 때는 표 전환과 같은 수준으로 알린다

## 7.3 P1-13 — 다른 배열을 기존 표에 연결하는 길이 드래그 하나뿐이다 **[신규]**

`testRows`라는 배열을 새로 선언하고 기존 표에 연결해 봤다.

| 방법 | 결과 |
|---|---|
| 팔레트 행의 **＋** 누르기 | **새 표가 하나 더 생긴다.** 표를 선택해 둬도 마찬가지 (`ArrayDrag.place`는 항상 새로 만든다) |
| 표 위로 **드래그** | **연결된다.** `source`가 `bound:testRows`로 바뀌고 열도 `testRows`의 자식으로 재구성된다 |

즉 **기능 자체는 있는데 발견할 수가 없다.**

- Inspector의 표 구조 섹션은 "왼쪽 데이터 패널의 배열을 이 표에 끌어다 놓으면 데이터
  표로 바뀝니다"라는 안내를 **정적 표일 때만** 보여 준다. 이미 데이터 표인 경우엔
  경로 칩과 "직접 입력한 행으로 바꾸기" 버튼만 있고, 다른 배열로 갈아탈 수 있다는
  말이 없다.
- 연결이 바뀌면서 **직접 추가한 `column3`이 말없이 사라진다**
  (`fromArrayChildrenKeepingWidth`가 열 구성을 통째로 교체한다).

### 필요한 것

표 구조 섹션에 **데이터 배열 선택 드롭다운**을 둔다. 드래그는 지름길로 남기고,
연결을 바꿀 때 사라지는 열을 미리 알린다.

## 7.4 정리 — 사용자가 옳았다

| 사용자 지적 | 확인 결과 |
