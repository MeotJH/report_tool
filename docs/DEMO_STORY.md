# 데모 유저 스토리

[apps/demo-host](../apps/demo-host/README.md)가 무엇을 보여야 하는지 정한다.

데모의 목적은 기능 자랑이 아니다. **"이 라이브러리를 우리 앱에 어떻게 넣는가"**와
**"넣으면 무엇이 안전해지는가"** 두 질문에 답하는 것이다. 그래서 화면 하나하나가
그 답의 한 조각이어야 하고, 답과 상관없는 화면은 넣지 않는다.

## 나오는 사람 셋

| 누구 | 무엇을 하나 | 이 사람에게 중요한 것 |
|---|---|---|
| **김인사** (인사담당자) | 양식을 만들고 발행한다 | 개발자가 아니다. JSON을 모른다 |
| **박개발** (호스트 백엔드) | Spring에서 `resolve()`를 구현한다 | **무슨 JSON을 만들어야 하는가** |
| **이직원** (수신자) | 링크로 받아 보고 서명한다 | 계정이 없다. 링크가 전부다 |

세 번째 사람이 있다는 것이 이 제품의 핵심이다. 문서는 만드는 사람과 받는 사람이
다르고, **받는 사람은 되돌릴 수 없는 것에 서명한다.**

---

## 1막 — 김인사가 양식을 만든다

1. `admin` / `admin`으로 로그인한다.
2. **양식 목록**이 비어 있다. `새 양식`을 누른다.
3. 편집기가 열린다. 제목을 놓고, 표를 만들고, 팔레트에서 변수를 선언해 끌어다 놓는다.
4. 주민등록번호를 선언할 때 **민감한 값**을 체크한다. 캔버스에 놓는 순간
   `900101*******7`로 가려진다.
5. 팔레트의 점 세 개가 어긋남을 알려 준다.

   ```
   ● ● ●  employee.name     선언됨 · 문서에서 씀 · 샘플에 있음
   ● ● ○  pay.bonus         샘플에 없다 — 지금 발행하면 빈칸이다
   ● ○ ●  employee.email    선언만 하고 쓰지 않는다
   ```

6. `저장`. 저장은 편집기가 아니라 **호스트 API**로 간다.

**이 막이 증명하는 것**: 편집기는 앱이 아니라 사내 시스템의 한 메뉴다. 자리 하나
내주고 생성자를 부르면 된다. 그리고 민감한 값은 **담당자가 아무것도 하지 않아도**
가려진다.

---

## 2막 — 박개발이 무슨 데이터를 줘야 하는지 안다

7. 양식 목록에서 그 양식의 **데이터 명세**를 연다.

   ```
   이 양식이 요구하는 데이터

     employee.name     문자   필수
     employee.number   문자   필수
     payments[]        배열
       .name / .amount
     netPay            금액   필수

     [샘플 JSON 복사]  [JSON Schema 내려받기]
   ```

8. 복사한 모양대로 Spring에서 `GET /report-api/data/{templateId}/{recipientId}`를
   구현한다.

**이 막이 증명하는 것**: 계약은 **설계의 출력**이지 입력이 아니다. 박개발은 양식
JSON을 뜯어보지 않는다. 김인사도 스키마 폼을 채우지 않는다. 김인사가 설계하면
도구가 "이제 이런 데이터가 필요해졌다"고 말한다.

---

## 3막 — 김인사가 발행한다

9. 양식 목록에서 **발행 가능으로 표시**. 이 표시가 없으면 사이드카가 거절한다 —
   만들다 만 양식이 직원에게 나가는 것을 막는 자리다.
10. **발행** 화면에서 받는 사람을 고른다.
11. `이 데이터로 시험 발행`을 누른다. 아무것도 저장하지 않는다.

    ```
    ✗ netPay 가 데이터에 없습니다 (필수)
    ✓ 나머지 12개 정상
    → PDF 미리보기
    ```

12. 박개발이 `netPay`를 채운다. 다시 눌러 통과하면 **진짜 발행**한다. 링크가 나온다.

**이 막이 증명하는 것**: **발행본은 되돌릴 수 없다.** 그래서 그 앞에 멈추는 자리가
있어야 한다. 그리고 필수 값이 없으면 발행 자체가 거절된다 — 지금까지는 빈칸으로
나갔고 아무도 몰랐다.

---

## 4막 — 이직원이 서명한다

13. 링크를 연다. **로그인하지 않는다.** 계정이 없다.
14. PDF가 뜬다. 주민등록번호는 가려져 있다.
15. 서명하고 제출한다.
16. 문서 상태가 `signed`가 되고, 감사 로그에 **이직원의 브라우저와 주소**가 남는다.

**이 막이 증명하는 것**: 링크에 든 서명 토큰이 그 사람의 자격이다. 그리고 남는
기록은 "무엇에 서명했는가"(PDF 해시)와 "누가 언제"(감사 로그) 둘 다다.

---

## 5막 — 실수를 되돌린다

17. 김인사가 양식을 고치려 한다. 발행본이라 잠겨 있다. **새 버전 만들기**를 누르면
    v2 초안이 생긴다. **이미 발행된 문서는 v1을 그대로 가리킨다.**
18. 잘못 만든 양식은 목록에서 **삭제**한다. 발행 이력이 있는 양식은 삭제 대신
    **보관**만 된다 — 지운 양식으로 발행한 문서가 근거를 잃으면 안 된다.

**이 막이 증명하는 것**: 버전은 장식이 아니다. 발행본이 가리키는 것이 바뀌면
"무엇에 서명했는가"에 답할 수 없다.

## 화면 목록

| 화면 | 경로 | 라이브러리인가 |
|---|---|---|
| 로그인 | `/login` | 호스트 |
| 양식 목록 | `/templates` | 호스트 |
| 데이터 명세 | `/templates/{id}/contract` | 호스트 (계산은 core) |
| 양식 설계 | `/design/{id}` | **편집기 라이브러리** |
| 발행 | `/issue` | 호스트 |
| 수신자 | `/sign?token=…` | **뷰어 라이브러리** |

라이브러리는 둘뿐이다. 나머지는 전부 고객사가 자기 언어로 만들 것들이고, 데모는
그 본보기다.

## 만드는 순서

- [x] **D1. 양식 목록 + CRUD** ✅ — 새로 만들기 · 열기 · 삭제 · 발행 표시 · 발행 취소.
      편집기가 `demo-payslip` 하나에 박혀 있는 것을 `/design/{id}`로 푼다
- [x] **D2. 계약 계산** ✅ — 선언 · 사용 · 샘플 세 목록을 맞춰 본다. 1막의 점 세 개,
      2막의 명세, 3막의 검사가 **모두 이 하나를 근거로 삼아야 한다**. 세 곳이 각자
      계산하면 반드시 갈라지고, 갈라지면 "편집기는 괜찮다는데 발행이 거절된다"가 된다.
      지금은 core를 건드리지 않고 호스트 쪽 `lib/templateContract.ts`에 두었다 —
      이미 공개된 `TemplateReferences`로 충분했다. D3이 라이브러리로 들어갈 때
      그때 core로 옮긴다
- [ ] **D3. 발행 시 필수 검사** — `IssuanceService`가 필수 누락이면 거절한다.
      필수의 기본값은 **문서에서 쓰이면 필수**이고, 설계자가 풀 수 있다.
      급여명세서에서 "그렸는데 빈칸이어도 된다"는 예외지 기본이 아니다
- [x] **D4. 데이터 명세 화면 + 샘플 JSON 복사** ✅ 박개발용
- [ ] **D5. 팔레트 점 세 개** — 김인사용
- [ ] **D6. 시험 발행** — 저장하지 않고 검사와 미리보기만
- [ ] **D7. 새 버전 만들기 · 보관** — 5막

D3까지가 "빈칸 발행 사고"를 막는 최소선이다.

**D3·D5는 라이브러리를 고쳐야 한다.** D3은 `IssuanceService`, D5는 `FieldPalette`다.
D6(시험 발행)을 호스트에 두면 같은 검사를 화면에서 먼저 보여 줄 수는 있지만,
**진짜 방어벽은 라이브러리 안에 있어야 한다** — 호스트가 검사를 빼먹으면 그대로
빈칸이 나간다.

## 만들면서 드러난 것

- **양식 CRUD는 호스트의 일이다.** `TemplateStore` 포트에 목록도 삭제도 없다.
  발행에 필요 없기 때문이다 — 사이드카는 양식을 읽기만 한다. 없는 것이 맞다.
- **발행 취소는 도메인이 지지하지 않는다.** `Template`에 `unpublish`가 없다.
  되돌려도 되는지는 발행 이력을 아는 쪽만 판단할 수 있고, 그것은 호스트다.
- **Next 호스트는 `serverExternalPackages`가 필요하다.** 빼면 라우트마다 core가
  따로 번들되어 `instanceof`가 조용히 거짓이 되고, Visitor가 요소를 하나도
  알아보지 못한다. 예외도 로그도 없다. 실제로 겪었다.
- **호스트 저장소는 살아 있는 객체가 아니라 JSON을 담아야 한다.** 그것이 실제
  DB의 모습이고, 위의 `instanceof` 사고도 함께 사라진다.
