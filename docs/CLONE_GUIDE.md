# 클론코딩 가이드

이 문서는 **"어떻게 만들었는지"를 기능 단위로 다시 물어볼 수 있게** 만든 색인이다.

각 단위는 커밋 하나에 대응한다. 커밋 하나 = 되짚을 수 있는 학습 단위 하나가 되도록
레이어와 기능으로 끊었다. 순서대로 따라가면 같은 결과에 도달한다.

## 이 문서를 쓰는 법

물어볼 때는 **단위 번호로** 부른다.

> "D2 클론코딩 해줘" → 단위 D2를 처음부터 다시 만드는 과정을 단계별로 설명한다
> "U3 왜 그렇게 했어?" → 단위 U3의 설계 판단만 되짚는다

| 접두사 | 레이어 | 실행 환경 |
|---|---|---|
| **D** | `packages/core` — domain / application | isomorphic |
| **R** | `packages/renderer` — PDF 출력 | node |
| **U** | `packages/designer` — 편집 화면 | browser |

**의존 방향은 항상 D → R·U다.** D를 먼저 만들지 않으면 R·U를 만들 수 없다.
클론코딩 순서도 같다.

각 단위의 코드는 `git show <해시>`로 통째로 볼 수 있다.

## 1차: 데이터 목록의 근거를 하나로 (D1 · U1)

### D1. 호스트가 주던 필드 스키마를 없앤다
`a0a3cef` · `packages/core/src/application/port/DataProvider.ts`, `index.ts`

**무엇을 푸는가**
연결 가능한 데이터 목록의 근거가 두 곳이었다. 호스트가 넘기는 `FieldSchema`와
템플릿이 선언한 `variables`. 같은 경로가 양쪽에 있으면 어느 쪽이 실제로 쓰이는지
화면에서도 코드에서도 판단할 수 없다.

**왜 이렇게 했는가**
근거는 하나여야 한다. 문서가 무엇을 필요로 하는지 아는 사람은 그 문서를 설계하는
담당자이므로, 템플릿의 `variables`를 유일한 근거로 남기고 `DataProvider`는 미리보기와
발행에 쓸 **데이터만** 공급하게 했다.

**만드는 순서**
1. `DataProvider`에서 `FieldSchema` 타입과 `fields()` 메서드를 지운다
2. `core/index.ts`의 `FieldSchema` export를 지운다
3. 타입 검사를 돌려 무너지는 곳을 전부 찾는다 — 그게 U1의 작업 목록이 된다

**완료 확인** `npm run typecheck:core` 통과.

## 2차: 편집기와 발행본을 일치시킨다 (D2 · R1 · U3)

이 묶음이 이 프로젝트에서 **가장 중요하다.** 캔버스와 PDF가 서로 다른 코드로
서로 다르게 틀리고 있었고, 그래서 담당자가 본 문서와 서명자가 받은 문서가 달랐다.

### D2. 문단을 지키는 TextLayout을 도메인으로 옮긴다
`3e492dc` · `packages/core/src/domain/text/TextLayout.ts`

**무엇을 푸는가**
`PdfTextLayout`이 사용자가 넣은 줄바꿈(`\n`)을 몰랐다. `WrapTextStrategy`가 공백으로만
쪼개서 `"말한다.\n1. 제품의 …\n3."`이 한 줄로 묶였고, pdf-lib이 그 안의 `\n`을 자기
줄높이로 또 쪼갰다. 두 줄바꿈 체계가 충돌해 서약서 제1조 각 호가 **3→1→4→2 순서로
겹쳐** 발행됐다.

**왜 도메인인가**
캔버스와 PDF가 각자 줄을 나누면 반드시 어긋난다. 계산은 하나여야 하므로 domain에 둔다.
**폭 측정만** `TextWidthMeasurer` 콜백으로 받는다 — domain은 폰트를 몰라야 한다.

**만드는 순서**
1. `renderer/pdf/PdfTextLayout.ts`를 `core/domain/text/TextLayout.ts`로 옮긴다
2. `layout()`이 가장 먼저 `text.split("\n")`으로 문단을 나누게 한다
3. 문단마다 기존 전략(wrap/shrink/truncate)을 적용하고 줄을 이어 붙인다
4. shrink는 문단마다 다른 배율을 낼 수 있으므로 **가장 작은 크기로 통일**한다
5. `heightMm()`을 더한다 — 넘침 판정에 쓴다

**완료 확인** `lines.every(line => !line.includes("\n"))`. 5줄짜리 조문이 5줄로 나온다.

---

### R1. 줄 계산과 셀 해석을 도메인에서 가져다 쓴다
`e86d166` · `PdfElementVisitor.ts`, `PdfDocumentRenderer.ts`, `UsedCharCollector.ts`

**무엇을 푸는가** 렌더러가 자기 계산을 버리고 도메인 것을 쓴다.

**놓치기 쉬운 것 — 여기가 함정이다**
`UsedCharCollector`도 표 셀을 해석한다. **폰트 수집이 렌더링과 다른 규칙을 쓰면
치환된 한글이 서브셋에서 빠져 발행본에 통째로 빈칸으로 나온다.** 세 곳(캔버스 포함)이
같은 계산을 쓰는 것이 정확성의 조건이다.

**완료 확인** `npm test`와 `npm run typecheck:renderer` 통과, 서약서 PDF 재발행.

### U3. 캔버스가 도메인 줄 계산을 쓰고 넘침을 숨기지 않는다
`03da300` · `CanvasTextMeasurer.ts`(신규), `KonvaElementVisitor.ts`, `TemplateIssueFinder.ts`

**무엇을 푸는가**

| | 이전 캔버스 | 이전 PDF |
|---|---|---|
| 문단 줄바꿈 | Konva가 지켰다 | **무시했다** |
| 넘치는 줄 | **조용히 지웠다** (`Konva.Text`에 height를 주면 안 그린다) | `frame.height`를 보지 않고 전부 그렸다 |

둘 다 틀렸고, **서로 다르게** 틀렸다.

**만드는 순서**
1. `CanvasTextMeasurer` — 2D 컨텍스트로 폭을 잰다. 브라우저 API를 만나는 곳은 여기뿐
2. `KonvaElementVisitor.createTextNode`가 `TextLayout`으로 줄을 계산하고,
   Konva에는 `wrap: "none"` + 계산된 줄만 넘긴다
3. 넘치면 `height`를 비워 Konva가 자르지 않게 하고 `verticalAlign`을 top으로 되돌린다
4. `TemplateIssueFinder`가 "문구 N줄이 요소 높이보다 길다"를 경고한다
   — **어느 쪽도 조용히 지우거나 조용히 넘치지 않는다**

**남는 차이** 두 측정기의 글리프 metric이 완전히 같지는 않아 경계 어절에서 드물게 줄이
갈릴 수 있다. 완전한 일치는 PDF 미리보기(`TASKS.md` T57-V)가 닫는다.

**완료 확인** 서약서 4호가 캔버스·PDF 양쪽에 다 나오고, 편집기가
`문구 5줄이 요소 높이보다 길다 (29mm 필요)`를 표시한다.

## 3차: 표를 쓸 수 있게 만든다 (U2 · D3 · U4)

### U2. 표 열 너비 합을 표 프레임 안에 유지한다
`ea50516` · `TableColumnFitter.ts`(신규), `TableEditor.ts`, `TemplateIssueFinder.ts`

**무엇을 푸는가**
`＋ 열 추가`가 20mm를 그냥 붙였다. `110 + 60` 표에 열을 더하면 합이 190mm인데 프레임은
170mm 그대로여서, 새 열이 **표 밖이자 A4 오른쪽 끝 바깥**에 생겼다.
`findElementAt`이 `frame.contains`로 판정하므로 그 열 위에는 데이터를 놓을 수도 누를
수도 없었다. **보이는데 만질 수 없는 열**이다.

**왜 비례 축소인가**
새 열이 폭을 새로 만들지 않고 기존 열에서 나눠 받게 하면 "열 너비 합 = 프레임 너비"가
불변으로 유지된다. 비례를 지키므로 "항목 열이 금액 열보다 넓다"는 의도도 남는다.

**만드는 순서**
1. `TableColumnFitter.fitToWidth(columns, totalWidthMm)` — 비례 유지 + 최소 폭 보장
2. 반올림 오차를 가장 넓은 열이 흡수하게 한다. 안 하면 열을 더할 때마다 오차가 쌓인다
3. `TableEditor.addColumn`/`removeColumn`이 결과에 보정을 적용
4. 보정 전에 저장된 템플릿을 위해 합이 어긋난 표를 경고로 드러낸다

**완료 확인** `110 + 60` → 열 추가 → `98.43 + 53.68 + 17.89 = 170`.
새 열 중앙에 팔레트 항목을 떨어뜨리면 그 열이 연결된다.

### D3. 표 셀을 두 단계로 해석한다
`b92988e` · `TableCellResolver.ts`(신규), `TemplateReferences.ts`

**무엇을 푸는가**
급여명세서 표의 대부분은 **항목 이름은 모든 문서에서 같고 금액만 사람마다 다르다.**
그런데 `TableSource`는 정적(전부 템플릿 저장)이거나 데이터(전부 배열)뿐이었다.
정적 셀에 `{{baseSalary}}`를 적으면 문자 그대로 발행됐고 경고도 없었다.

**설계**
1. 열의 `cellTemplate`(`{{row.amount}}`)이 **행에서** 값을 꺼낸다
2. 그 값이 다시 표현식이면 **문서 데이터로** 채운다

치환은 정확히 두 번이다. 데이터가 데이터를 가리키게 두면 순환을 막을 수 없고,
무엇이 찍힐지 사람이 읽어서 예측할 수도 없다.

**만드는 순서**
1. `TableCellResolver.resolve(column, row, data)` — 두 번의 `TemplateExpression.render`
2. `resolveRow` / `resolveRowSource` — 후자는 설계 화면용(1단계까지만)
3. `TemplateReferences`가 정적 셀 안의 경로도 모으게 한다 → 오타가 경고로 잡힌다

**완료 확인** `기본급 | {{pay.base}}` 표가 PDF에서 `기본급 | 4200000`으로 나오고,
같은 표에 섞은 순수 고정 문구 행은 그대로 유지된다.

### U4. 정적 표의 저장된 행을 설계 화면에 보여준다
`0e0ddf0` · `KonvaElementVisitor.ts`

**무엇을 푸는가**
정적 표가 설계 모드에서 저장된 행 대신 `⟨key⟩` 한 줄만 보여 줬다. 행이 3개여도 화면에는
1줄. 그런데 `TableCellLocator`는 3행 전부를 편집 대상으로 인정하므로,
**보이지 않는 칸을 더블클릭해 편집하는** 상태였다.

**설계 판단**
정적 행은 데이터가 아니라 사용자가 템플릿에 써 넣은 문서 내용이므로 전부 그린다.
다만 셀에 적은 표현식은 **값으로 바꾸지 않는다** — 캔버스에 금액이 보이는데 그 칸을
더블클릭하면 표현식이 나타나면 둘이 어긋난다. 설계는 "무엇이 연결됐는가",
미리보기는 "무엇이 찍히는가"를 보여 준다.

**완료 확인** 정적 행 3개가 각각 그려진다(Konva 씬 그래프에서 6개 Text).

### U5. 표 연결을 Inspector 드롭다운으로 고른다
`73a0a35` · `ElementInspectorVisitor.tsx`, `TableEditor.ts`, `InspectorPanel.tsx`

**무엇을 푸는가**
표를 데이터에 붙이는 길이 **팔레트 드래그 하나뿐**이었다. 안내가 없었고, 좌표에
의존하므로 U2 이전에는 열이 표 밖으로 밀려나 드롭 자체가 되지 않았다.
`＋` 버튼은 늘 새 표를 만들어서 기존 표에 연결할 수단이 없었다.

**만드는 순서**
1. `DesignerShell`이 이미 계산한 `entries`를 `InspectorPanel` → 방문자로 내린다
   (다시 계산하면 팔레트와 Inspector가 다른 목록을 볼 수 있다)
2. 표 구조에 **행 출처** 드롭다운 — 직접 입력한 행 + 선언된 배열
3. 열 카드에 **데이터** 드롭다운 — 연결 안 함 + 그 배열의 자식
4. 정적 표에서는 열 드롭다운을 숨긴다. 값을 정하는 단위가 열이 아니라 **셀**이다
5. 전환으로 사라지는 행·열을 `setNotice`로 알린다

**놓치기 쉬운 것**
배열 연결 규칙을 `ArrayDrag`가 혼자 갖고 있었다. 드롭다운이 같은 규칙을 다시
구현하면 **"끌어다 놓았을 때"와 "골랐을 때"의 결과가 갈린다.**
`TableEditor.bindArray`로 옮겨 두 경로가 함께 쓰게 했다 — 이 프로젝트에서
반복해서 나오는 실수 유형이다(D2·D3와 같은 종류).

헤더는 사용자가 이미 고쳤을 수 있으므로 함부로 덮지 않는다. 비어 있거나 자동
이름(`열 3`)일 때만 자식의 표시 이름으로 바꾼다.

**완료 확인** 드래그 없이 새 열을 `payItems.test`에 연결하고, 표 전체를
`testRows`로 갈아탄다. 갈아탈 때 `열 구성 3개가 배열 구조로 바뀌었습니다`가 뜬다.

## 4차: 리포트를 발행할 수 있게 만든다 (D4 ~ D8 · U6 · R2)

여기부터는 문서 종류가 바뀐다. 3차까지는 **한 사람당 한 장**짜리 양식(급여명세서·
서약서)이었고, 4차는 **건수가 흘러 넘치는 리포트**(월간 서비스 리포트)다.
행 수가 데이터로 정해지고, 표가 쪽을 넘고, 쪽마다 번호가 붙는다.

이 차수의 기준 문서는 `packages/renderer/src/pdf/ServiceReportTestFixture.ts`다.
"만들 수 있다"의 판정은 그 픽스처가 실제 PDF로 나오는지로 한다.

### D4. 표가 그려지는 줄을 도메인 한 곳에서 정한다
`b349ad6` · `core/domain/layout/TableLayout.ts`, `TableCellText.ts`, `TableSource.ts`

**무엇을 푸는가**
같은 표가 화면마다 다른 줄 수로 보였다. 설계 화면은 자리표시자 한 줄, 미리보기는
앞의 세 줄, 발행본은 영역에 들어가는 만큼. 담당자는 여유 있어 보이는 표를 만들고
발행본에서는 행이 말없이 사라졌다.

**왜 이렇게 했는가**
줄을 정하는 규칙이 세 곳에 있으면 반드시 갈라진다. `TableLayout` 하나가 정하고
셋이 그 결과만 그린다. 설계와 발행의 차이는 `TableCellText` 전략 하나로 좁혔다 —
설계는 셀에 적은 표현식을 보존하고 발행은 데이터까지 채우되, **줄 수와 자르는
규칙은 완전히 같다.**

**만드는 순서**
1. `TableLayout.compute(표, 데이터) → { rows, ... }` — 머리글 + 본문을 한 목록으로
2. `TableCellText.resolved()` / `.source()` — 셀 문자열을 만드는 방식만 다르게
3. `TableSource.deferredRows()` — 행 수가 발행 시점에 정해지는 출처인지 알린다.
   비어 있는 데이터 표에만 자리표시자를 만들고, 행을 지운 정적 표에는 만들지 않는다
4. 캔버스·PDF·`UsedCharCollector`가 각자 하던 계산을 지우고 이 결과를 쓴다
5. `TemplateIssueFinder`에 "빠지는 줄" 경고를 더한다

**완료 확인** 같은 데이터면 세 화면의 줄 수가 같다. 빠지는 줄이 있으면 경고가 뜬다.

### D5. 표 행 높이를 셀 내용에 맞춘다
`4c340f9` · `core/domain/layout/TableRowHeights.ts`, `domain/text/TextLayout.ts`

**무엇을 푸는가**
행 높이가 고정이라 긴 문장을 담은 칸이 아랫줄을 덮었다. 리포트의 요청내용은 스무
줄이 넘는다.

**왜 이렇게 했는가**
글자 폭은 폰트만 안다. 그래서 도메인이 직접 재지 않고 **잴 수 있는 곳에서 측정기를
받는다**(`StyleMeasurerFactory`). 늘리기만 하고 줄이지는 않는다 — 지정한 행 높이는
담당자가 보기 좋으라고 정한 값이다.

**만드는 순서**
1. `TableRowHeights.fixed()` / `.content(측정기)` — 두 방식을 전략으로 나눈다
2. `TableLayout`이 줄마다 이 전략에 높이를 묻는다
3. PDF는 임베딩 폰트, 캔버스는 2D 컨텍스트를 측정기로 넘긴다
4. `TextLayout`의 wrap 전략에 **글자 단위 줄바꿈**을 더한다 — 공백만 찾으면 칸보다
   긴 한글 어절이 끊기지 않아 칸 밖으로 뻗는다
5. Konva의 안쪽 여백만큼 쓸 수 있는 높이가 준다는 것을 계산에 반영한다.
   빼지 않으면 딱 맞게 계산된 마지막 줄을 Konva가 조용히 지운다

**완료 확인** 긴 셀이 여러 줄로 나뉘고 그만큼 행이 커지며 아래 행이 밀린다.

### D6. 표가 쪽을 넘어 이어지고 머리글이 반복된다
`5a49605` · `core/domain/layout/DocumentLayout.ts`, `renderer/pdf/PdfFontBook.ts`

**무엇을 푸는가**
스물세 건은 어느 자리에도 한 번에 들어가지 않는다. 지금까지는 들어가는 만큼만
그리고 나머지를 버렸다.

**왜 이렇게 했는가**
**쪽 수는 저장된 값이 아니라 데이터가 정한다.** 그래서 "몇 쪽인가"는 도메인이
계산해야 한다. 렌더러가 각자 하면 편집기가 본 쪽 수와 발행본의 쪽 수가 갈린다.

**만드는 순서**
1. `TableLayout.compute`에 조각 옵션을 더한다 — 시작 행·쓸 수 있는 높이,
   결과에 `nextBodyRowIndex`("다음은 여기부터")
2. `DocumentLayout.compute(템플릿, 데이터) → PageLayout[]`
3. 이어지는 표는 본문 영역 맨 위에, **원래 가로 자리와 너비 그대로** 놓는다
4. 조각마다 열 이름 줄을 다시 그린다
5. **진행 보장**: 새 쪽에도 들어가지 않는 줄이면 머리글을 포기하고 본문 한 줄을
   반드시 그린다. 안 그러면 쪽이 무한히 늘어난다(테스트 워커가 죽어서 발견했다)
6. 칸 역할 판정 근거를 줄 번호에서 **본문 행 번호**로 바꾼다 — 쪽이 넘어가면 같은
   행이라도 쪽 안에서의 줄 번호가 달라져 둘째 쪽 첫 행이 머리글로 칠해진다
7. `PdfFontBook` — 폰트를 찾고 폭을 재는 규칙을 하나로 모은다. 배치는 그리기 전에
   폭을 재야 하는데, 두 곳이 각자 폰트를 찾으면 잰 폭과 그릴 폰트가 달라진다

**완료 확인** 23건이 두 쪽으로 이어지고 둘째 쪽에 열 이름이 다시 나온다.
건수를 늘리면 쪽 수가 늘어난다.

### D7. 요소가 어느 쪽에 놓이는지 저장한다 (schemaVersion 2)
`4a302c2` · `core/domain/element/Element.ts` 외 7종, `TemplateFactory.ts`

**무엇을 푸는가** 표지 한 장 + 본문 여러 장짜리 문서를 만들 수 없었다.

**왜 이렇게 했는가**
쪽 수를 따로 저장하지 않고 요소가 가진 쪽 번호로 센다. 두 곳에 저장하면 요소를
지웠을 때 빈 쪽이 남을지 사라질지가 **두 값 중 무엇을 믿느냐**에 따라 갈린다.

**만드는 순서**
1. `Element`의 공통 상태에 `pageIndex`를 더하고 일곱 종류 생성자에 통과시킨다
2. `ElementFactory`가 읽고 쓴다. 없으면 0 — 그때는 문서가 한 장뿐이었다
3. `TemplateFactory`가 버전 1과 2를 모두 연다. 다시 저장하면 2로 올라간다
4. `DocumentLayout`이 저작 쪽을 차례로 내보내되 **어떤 쪽의 표가 넘치면 그 쪽 바로
   뒤에** 이어지는 쪽을 넣는다. 안 그러면 표지 → 처리내역 1~4 → 기타사항 →
   처리내역 5~23이 되어 읽을 수 없다
5. `ElementCommonState.test.ts`에 일곱 종류 전부를 도는 안전망을 더한다.
   한 종류라도 `with` 메서드에서 빠뜨리면 그 요소는 편집하는 순간 첫 쪽으로 돌아간다

**완료 확인** 버전 1 문서가 그대로 열리고 모든 요소가 첫 쪽에 놓인다.

### U6. 편집 화면이 쪽을 오간다
`91a6c73` · `EditorController.ts`, `DesignerShell.tsx`, `LayersPanel.tsx`, `CanvasStage.ts`

**무엇을 푸는가** 저장 형식에는 쪽이 생겼는데 화면에는 첫 쪽만 있었다.

**왜 이렇게 했는가**
새 요소에 쪽 번호를 붙이는 일을 `EditorController.placeNewElement` 하나로 모았다.
도구·팔레트 드롭·배열 드롭이 각자 붙이면 **한 곳만 빠뜨려도 그 요소는 첫 쪽에
생기고, 만든 사람 눈에는 요소가 나타나지 않는다.**

**만드는 순서**
1. 컨트롤러에 `activePageIndex` + `pageCount()`(빈 새 쪽 한 장 포함)
2. `placeNewElement` — 세 곳이 반복하던 추가·선택·도구 복귀도 함께 모은다
3. 캔버스·레이어·선택·판정을 보고 있는 쪽으로 좁힌다.
   다른 쪽 요소가 목록에 있으면 고른 것이 화면에 없고, 그 상태의 Delete는
   보이지 않는 것을 지운다
4. 쪽 이동 막대(`‹ 2 / 3 › ＋ 쪽`)
5. 빈 쪽은 저장되지 않으므로 `빈 쪽` 표시를 붙인다

**완료 확인** `＋ 쪽` → 요소를 그리면 저장 JSON에 `pageIndex: 1`로 남는다.

### D8. 머리글·바닥글이 모든 쪽에 반복되고 쪽 번호가 찍힌다
`cccf820` · `core/domain/layout/PageNumbering.ts`, `Element.ts`, `DocumentLayout.ts`

**무엇을 푸는가** 쪽마다 `01 / 10`을 달아야 하는데 쪽마다 따로 만들 수 없다.

**왜 이렇게 했는가**
**쪽 번호는 데이터가 아니라 배치의 결과다.** 발행할 데이터에는 "몇 쪽인지"가 없고
표가 다 흐른 뒤에야 정해진다. 그래서 데이터 치환과 섞지 않고 배치가 끝난 뒤 채운다.

**만드는 순서**
1. 요소 공통 상태에 `repeated`를 더한다(D7과 같은 통로)
2. `PageNumbering` — `{{page}}` `{{pages}}`, 자릿수는 `{{page:00}}`.
   자리보다 큰 수는 자르지 않는다. 자르면 10쪽짜리의 10쪽이 0쪽이 된다
3. `DocumentLayout`이 배치를 끝낸 뒤 반복 요소를 **맨 뒤에** 얹고 번호를 채운다
4. 캔버스도 같은 `PageNumbering`으로 지금 쪽 번호를 채워 보여 준다
5. 반복 요소는 어느 쪽에서도 보이고 고칠 수 있게 한다

**완료 확인** 두 쪽짜리 PDF의 바닥글이 `01 / 02`, `02 / 02`로 찍힌다.

### U7. 편집기가 발행본과 같은 글꼴 파일로 잰다
`<이 커밋>` · `designer/view/FontLibrary.ts`, `CanvasTextMeasurer.ts`, `Designer.ts`

**무엇을 푸는가**
편집기는 `100px Pretendard`처럼 **가족 이름**으로 글자를 쟀다. 그 이름은 보는 사람
컴퓨터에 깔린 글꼴로 해석되며 렌더러가 임베딩하는 파일이 아니다. 실제로 숫자 폭이
7% 어긋났고(0.555em vs 0.596em), 48mm 칸이면 3.4mm — 줄바꿈이 한 어절씩 달라진다.
담당자 PC에 그 글꼴이 없으면 사람마다 편집 화면이 달라진다.

**왜 이렇게 했는가**
등록할 때 **다른 이름**을 쓴다(`rt-embedded-Pretendard`). 원래 이름으로 등록하면
시스템 글꼴과 구분할 수 없어, 파일을 못 받았을 때도 조용히 다른 글꼴로 재고 있는
것을 아무도 모른다. 이름이 다르면 못 받은 사실이 드러난다.

렌더러와 **같은 포트**(`FontProvider`)를 쓴다. 호스트가 한 곳에만 글꼴을 주면
편집기와 발행본이 같은 파일을 본다.

**만드는 순서**
1. `FontLibrary` — 등록기(`FontFaceRegistrar`)를 주입받아 브라우저 없이도 규칙을
   검증할 수 있게 한다. `familyFor` / `isFileBacked` / `missingFamilies`
2. 굵기 하나라도 못 받으면 그 가족은 파일 기반이 아니다. 보통 굵기만 받고 굵은
   글씨를 브라우저가 흉내 내면 그 폭은 발행본과 다르다
3. `CanvasTextMeasurer`와 Konva의 `fontFamily`가 **같은 이름**을 쓴다.
   재는 글꼴과 그리는 글꼴이 다르면 계산한 줄과 보이는 줄이 어긋난다
4. `Designer`가 시작할 때 파일을 받아 등록하고 **다시 그린다**
5. 못 받은 글꼴은 화면이 경고로 표시한다

**완료 확인** 브라우저에서 `rt-embedded-Pretendard`로 잰 폭이 임베딩 파일과 같다.
