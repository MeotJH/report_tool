# 리포트형 문서 로드맵

이 문서는 **월간 서비스 리포트**(고객사에 매달 나가는 10쪽짜리 e-HR 리포트)를
담당자가 직접 만들 수 있게 하는 작업 순서다.

기존 [TASKS_NEXT.md](TASKS_NEXT.md)(N00~N19)는 **한 사람당 한 장**짜리 양식
(급여명세서·비밀유지서약서)을 기준으로 잡은 순서다. 리포트는 문서 종류가 다르다 —
행 수가 데이터로 정해지고, 표가 쪽을 넘고, 쪽마다 번호가 붙는다. 그래서 순서를
다시 잡았다. **N05~N19의 항목은 여기 7~13단계에 흡수돼 있다.**

기준 문서는 `packages/renderer/src/pdf/ServiceReportTestFixture.ts`다.
"됐다"의 판정은 그 픽스처가 실제 PDF로 나오는지로 한다.

- 원본(고객사 자료): 저장소에 두지 않는다. 담당자가 `인팩 리포트.pdf`로 가지고 있다
- 재현본: `npx vitest run packages/renderer` → `apps/poc/generated-service-report.pdf`
  (`.pdf`는 `.gitignore` 대상이라 커밋되지 않는다. 필요할 때 다시 만든다)

## 실물로 확인한 구멍

`85e0da5`의 픽스처로 3쪽짜리 PDF를 만들어 원본과 나란히 비교한 결과다.

### A. 편집기와 발행본이 서로 다른 폰트로 글자 폭을 잰다 🔴

같은 브라우저에서 같은 이름으로 잰 결과다.

| 재는 대상 | `-` | `0` |
|---|---|---|
| 실제 임베딩되는 TTF 파일 (PDF가 쓰는 것) | 0.433em | 0.596em |
| `Pretendard`라는 **이름**으로 잰 것 (편집기가 쓰는 것) | 0.348em | 0.555em |

`CanvasTextMeasurer`는 `100px Pretendard`처럼 **가족 이름**으로 잰다. 그 이름은
보는 사람 컴퓨터에 깔린 폰트로 해석되며, 렌더러가 임베딩하는 파일이 아니다.
숫자 폭만 7% 차이고 48mm 칸이면 3.4mm — 줄바꿈이 한 어절씩 달라진다.
담당자 PC에 그 글꼴이 없으면 **사람마다 편집 화면이 다르다.**

2단계에서 "줄 계산을 하나로 모았다"고 했지만 그 계산의 **입력값이 두 세계에서
다른 파일에서 왔다.**

**고쳤다(U7).** 렌더러의 `FontProvider` 포트를 편집기도 쓴다. 호스트가 준 TTF를
`FontFace`로 등록하되 **다른 이름**(`rt-embedded-<가족>`)으로 등록한다. 원래 이름
그대로 등록하면 시스템에 깔린 같은 이름의 글꼴과 구분할 수 없어, 파일을 못 받았을
때도 조용히 다른 글꼴로 재게 된다. 이름이 다르면 못 받은 사실이 드러나고, 화면이
`글꼴 X 파일을 받지 못해 화면 줄바꿈이 발행본과 다를 수 있다`로 알린다.

확인: 브라우저에서 `rt-embedded-Pretendard`로 잰 `-`는 0.433em·`0`은 0.596em으로
**임베딩 파일과 정확히 같다**(시스템 `Pretendard`는 0.348em·0.555em).

### B. 이어지는 쪽에 표 캡션이 따라가지 않는다 🟠

3쪽에는 표만 있고 `처리내역 (상세)`·`기간 …`이 없다. 원본은 매 쪽에 있다.
`모든 쪽에 반복`을 켜면 표지에도 나오므로 맞지 않다 — **"표가 이어질 때 그 표에
딸린 캡션도 함께 간다"**는 개념이 따로 필요하다.

### C. 고정 문구 안의 `{{ }}`가 경고 없이 그대로 발행된다 🟠

표지에 `-{{customer.shortName}}-`가 코드 그대로 찍혔다. 문구 종류를 `고정 문구`로
두면 치환하지 않는 것이 맞지만, **처음 쓰는 사람이 반드시 밟는 함정**이다.
참조 검사는 데이터 문구만 보므로 이 자리를 영영 지나쳤다.

**고쳤다(U8).** 고정 문구에 데이터 표현식이 남아 있으면 경고한다. 쪽 번호
(`{{page}}`)는 고정 문구에서도 채워지므로 지적하지 않는다 — 그 판단은
`PageNumbering.isPageToken`이 갖는다.

### D~F. 예상하던 것들 🟡

- 로고·직인 이미지를 못 넣는다 (12단계)
- 셀 병합이 없어 표지 하단 회사 표를 못 만든다 (8단계)
- 열 폭이 모자라면 날짜가 `2026- 07- 01`로 접히는데 알려 주지 않는다.
  글자 단위 줄바꿈은 의도대로 동작한 것이고, **"이 열은 날짜가 안 들어간다"고
  알려 주는 쪽**이 맞다

높이가 바뀌는 순간 바로 깨진다.

### 남은 넷은 무엇인가

세 가지 원인이고, 셋 다 **엔진이 아니라 재료**의 문제다.

1. **글자 폭 측정의 소수점** — 우리는 pdf-lib로, 원본은 자기 도구로 잰다. 349줄 중
   서너 줄에서 마지막 한 글자가 이쪽 줄에 남느냐 다음 줄로 가느냐가 갈린다
2. **원본 원문을 되살릴 수 없는 부분** — 처리 건의 문장은 원본 PDF에서 뽑아낸
   것이다. 줄 끝에서 사라진 공백은 PDF에 흔적이 남지 않는다. 행 높이가 증명하는
   빈 줄은 되살렸지만(`tools/report-fidelity` 참고) 공백은 되살릴 수 없다
3. **원본 도구의 이중 간격** — 원본은 행 높이를 재는 간격(14.69pt)과 글자를 쌓는
   간격(12.03pt)을 따로 쓴다. 우리는 하나로 쓴다. 둘로 나누면 화면에서 잰 줄과
   발행본에 찍히는 줄이 갈리고, 그 차이는 발행본에서만 드러난다. **일부러 따르지
   않았다**

### 지금 상태에서 알아 두어야 할 제약

- **편집 화면은 한 번에 한 쪽만 보여 준다.** 쪽 이동 막대(`‹ 2 / 3 › ＋ 쪽`)로 오간다.
  세로로 이어 보는 방식은 좌표계를 전부 바꿔야 해서 뒤로 미뤘다(U6 참고)
- **빈 쪽은 저장되지 않는다.** 쪽 수는 요소가 정하기 때문이다. 요소를 놓아야 남는다
- **호스트는 글꼴 파일을 줘야 한다.** `DesignerOptions.fontProvider`를 주지 않으면
  편집기가 시스템 글꼴로 재고, 화면 줄바꿈이 발행본과 달라진다(U7 참고).
  플레이그라운드의 `PlaygroundFontProvider`가 호스트가 할 일의 전부다
- **집계는 호스트가 계산해 준다.** 합계 행도 데이터 배열에 들어 있어야 한다
- 발행 렌더러는 **서버에서만** 돈다. 브라우저에서 호출하면 즉시 거부한다

## 이 단계들이 만든 도메인 구조

```
core/domain/layout/
  DocumentLayout    문서 하나 → 쪽 목록      (쪽 수는 데이터가 정한다)
  TableLayout       표 하나 → 이 자리에 그릴 줄 목록 + "다음은 여기부터"
  TableRowHeights   줄 하나 → 높이·줄 목록   (fixed / content 전략)
  TableCellText     칸 하나 → 문자열         (source / resolved 전략)
  TableCellSpans    줄 하나 → 칸마다 덮는 열 수
  TableRowSplit     행 하나 → 이 쪽 몫과 다음 쪽 몫
  TableGroup        표 + 딸린 요소 → 함께 옮길 덩어리
  PageNumbering     문구 → 쪽 번호를 채운 문구

core/domain/text/
  LineBreakUnits    문구 → 줄을 바꿔도 되는 자리 (한글은 글자마다)
```

**의존 방향**: 캔버스와 PDF는 이 결과를 *그리기만* 한다. 줄 수·높이·역할·쪽 나눔을
다시 판단하지 않는다. 판단이 두 곳에 있으면 반드시 갈라지고, 갈라진 것은 발행본에서만
드러난다.
