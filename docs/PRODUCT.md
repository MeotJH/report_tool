# 제품 설명

## 한 문단 정의

담당자가 브라우저 캔버스 위에서 급여명세서·계약서 같은 서류 양식을 직접 그려 만들고,
그 양식의 각 위치에 DB 필드(급여액, 성명 등)를 1:1로 연결해 템플릿으로 저장한 뒤,
발행 시점에 실제 직원 데이터를 결합해 문서를 확정·동결하고 링크로 배포하면,
직원이 열람 후 전자서명을 남길 수 있는 시스템을 — 특정 서비스에 종속되지 않고
다른 솔루션에 붙여 쓸 수 있는 자바스크립트 라이브러리/API 형태로 만든다.

---

## 1. 누가 쓰는가

| 역할 | 하는 일 | 사용하는 패키지 |
|---|---|---|
| **호스트 개발자** | 자사 솔루션에 라이브러리를 붙이고, 어댑터를 구현해 자사 DB·스토리지를 연결 | 전부 |
| **양식 담당자** (인사팀) | 캔버스로 양식을 설계하고 필드를 연결, 발행 | `designer` |
| **수신자** (직원) | 링크로 문서를 열람하고 서명 | `viewer` |

---

## 2. 전체 흐름

```
[설계]      담당자가 캔버스에 양식을 그린다
              → 각 요소에 데이터 필드를 드롭다운으로 연결
              → 템플릿(JSON) 저장 → 발행(publish) 시 해당 버전은 불변이 된다

[발행]      대상 직원 선택 → 서버가 실제 데이터를 조회
              → 템플릿 + 데이터 결합 → PDF 생성 → SHA-256 해시 계산
              → { 템플릿버전 + 데이터스냅샷 + PDF해시 } 를 동결 저장

[배포]      문서 1건당 1회용 단기 만료 토큰 발급 → 링크 전달

[열람·서명] 수신자가 링크로 접속 → 동결된 PDF 열람
              → 캔버스에 서명 → 스트로크 + PDF해시 + 본인확인수단을 함께 기록
```

### 왜 "동결"인가 — 이 제품의 핵심 규칙

발행되는 순간 문서는 불변이 된다. 이후 담당자가 템플릿을 수정하거나
DB의 급여액이 정정돼도 **이미 발행된 문서는 바뀌지 않는다.**

동결하지 않으면 "직원이 서명한 것이 정확히 무엇이었는가"를 증명할 수 없고,
그 순간 전자서명은 법적으로 무의미해진다. 이것이 데모와 상용 제품을 가르는 지점이다.

### 왜 렌더를 서버에서 하는가

클라이언트에서 최종본을 만들면 클라이언트가 결과물을 통제한다.
직원이 콘솔에서 `render(template, { netPay: 99999999 })`를 호출하면
진짜처럼 생긴 **위조 명세서**가 만들어진다.

따라서 렌더러는 Node·브라우저 양쪽에서 동일하게 동작하되, 두 등급으로 나눈다.

| 모드 | 실행 위치 | 용도 | 특징 |
|---|---|---|---|
| `preview` | 브라우저 | 담당자 미리보기 | **워터마크 강제**, 해시 대상 아님 |
| `authoritative` | 서버 전용 | 실제 발행본 | 해시 계산 대상, 브라우저에서 호출 시 예외 |

> 라이브러리는 실수를 막을 수 있을 뿐 공격을 막지는 못한다.
> 강제력은 "서버가 최종본을 만든다"는 아키텍처에서 나온다.

---

## 3. 왜 라이브러리가 I/O를 하지 않는가

급여명세서에는 주민등록번호·계좌번호·급여액이 들어간다.
고객사는 이 데이터가 외부로 나가는 것을 승인하지 않는다.

그래서 라이브러리는 `fetch` / `localStorage` / `fs` / DB를 **직접 호출하지 않는다.**
필요한 것은 전부 포트 인터페이스로 선언하고, 구현은 호스트가 자기 인프라에 맞춰 제공한다.

```ts
const designer = new Designer({
  container: document.querySelector('#root')!,
  templateStore,   // 호스트가 구현 — 라이브러리는 저장 위치를 모른다
  dataProvider,    // 호스트가 구현 — 라이브러리는 DB를 모른다
});
```

이 구조 덕분에 고객사는 사내 PostgreSQL이든 S3든 NAS든 그대로 꽂아 쓸 수 있고,
데이터는 고객사 경계를 벗어나지 않는다.

## 4. MVP 범위

전 단계가 끝까지 동작하되 각 단계는 최소 기능만 갖춘 **얇은 수직 슬라이스**로 만든다.

| 단계 | MVP | v1 이후 |
|---|---|---|
| 설계 | 텍스트·필드·이미지·박스·선, 단순 반복 테이블 | 조건부 표시, 다중 페이지, 페이지 넘침 자동분할 |
| 바인딩 | 드롭다운 선택, 포맷터(통화·날짜·숫자·마스킹) | 계산식, 집계 |
| 발행 | 데이터 동결 + 서버 PDF + SHA-256 | 대량 발행 큐, 재발행 정책 |
| 배포 | 1회용 단기 만료 토큰 링크 | 메일·카카오 알림, 만료 재발급 |
| 서명 | 단일 서명자, 스트로크 + PNG, 감사로그 | 다중·순차 서명자, PAdES/RFC3161 타임스탬프 |
| 본인확인 | 링크 토큰만 | SMS OTP, 사내 SSO |

### MVP에서 명시적으로 제외하는 것
협업 편집, 템플릿 마켓, 다국어, 접근성 HTML 뷰, 모바일 전용 UI.

## 5. 도메인 제약 (한국)

- **근로기준법 제48조 2항** — 임금명세서 교부 의무. 필수 기재사항이 정해져 있다:
  성명·생년월일 등 근로자 특정정보, 임금지급일, 임금총액, **항목별 금액**,
  **계산 방법**, 공제 항목별 금액. → 템플릿 검증기가 필수 항목 누락을 경고한다.
  (시행 전 현행 요건 재확인 필요)
- **전자서명법**(2020 개정) — 공인인증서 독점이 폐지되어 자체 전자서명도 효력이 있다.
  다만 분쟁 시 **본인확인**과 **무결성**을 입증해야 하므로 감사로그와 해시가 필수다.
- **개인정보** — 주민번호·계좌번호는 마스킹 포맷터를 기본값으로 제안한다.
  `DataProvider.sample()`은 반드시 마스킹된 값을 반환해야 한다.

---

## 6. 성공 기준

1. 담당자가 개발자 도움 없이 급여명세서 양식을 처음부터 만들 수 있다.
2. 화면 미리보기와 발행된 PDF의 글자 위치가 육안으로 구분되지 않는다.
3. 발행된 문서를 1년 뒤에 재렌더해도 바이트 단위로 동일하다.
4. 호스트 개발자가 어댑터 5개만 구현하면 붙는다.
